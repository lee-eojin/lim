コーディングエージェントはコードを速く書きます。しかし、自分の間違いに気づくのはずっと苦手です。変更を書いたエージェントは、その変更の最も弱いレビュアーです。自分の推論を通して変更を読むので、自分自身に同意してしまうからです。その結果、作業はレビューなしでコミットされるか、変更を書いたのと同じコンテキストによるレビューだけでコミットされます。

**LIMはこの問題への私の答えです。1つの仕事だけを行う小さなプラグインを、裏付けとなる数値と一緒に提供します。** 中心はreview-loopで、その隣でverifyとclear-explainが働きます。

![review-loopの実行例。レビュアーが2倍になった価格をP2として指摘し、修正が入り、2回目のレビューで指摘なしとなって停止し、最後に要約の表が出ます](../../docs/demo/review-loop.gif)

<sub>ループ、チェック、レビューのレポートは本物です。指摘とコードの変更は録画用に用意したもので、start、next、ruleの後の行はそのJSONの要約です。`vhs docs/demo/review-loop.tape`で作り直せます。</sub>

**review-loopは「コミットしてよい」を「レビュー済み」という意味にします。** まずプロジェクトのテスト、型チェック、lintを実行します。対象はNode.js、Python、Go、Rust、Java(GradleまたはMaven)、.NET、Ruby、Makefileのプロジェクトで、変更が触れるサブフォルダのプロジェクトも1ラウンドに最大4つまで含みます。次に、Claudeの推論を一切見ない新しいコンテキストのレビュアーが、指摘にP1からP5のラベルを付けます。重大な指摘には根拠を示さなければなりません。ClaudeがP1とP2を修正し、新しいレビュアーがその修正を確認します。いつ停止するかは、モデルではなくスクリプトが決めます。残りは、最後にユーザーが1回だけ判断します。

**機能を実行して証明します。** [verify](../../plugins/verify)を使うと、機能を実行するチェックがレビュー対象のコードで失敗したときに、指摘が再現されたとみなします。その修正は、同じチェックが再び通ったときにだけ認められます。

**何度も繰り返す指摘はルールになります。** 指摘に「ルールにする」を選ぶと、Claudeがlintルールかテストの下書きを書きます。review-loopはその下書きを修正前のコードに対して実行し、間違いを検出できることを証明します。バグ修正にも、同じ方法で回帰テストが付きます。

**意図的に小さく。** review-loopがセッションに追加するのは約275トークンです。hookは、ユーザーがリポジトリで有効にするまで何もしません。何かをインストールするときは、それが何か、どう削除するかを必ず先に伝えます。

フォークして、変更して、自分のものにしてください。Issueとpull requestを歓迎します。

## インストール

Claude Code、git、Node.js 18以降が必要です。

```
/plugin marketplace add lee-eojin/lim
/plugin install review-loop@lim
```

Claude Codeが再起動を求めた場合は、再起動します。marketplaceを追加すると、カタログが登録されるだけです。各プラグインは個別にインストールするため、ユーザーが選んだプラグインだけが入ります。

## はじめに

手順は2つです。

1. 上記のとおりreview-loopをインストールします。
2. コミットしていない変更があるgitリポジトリで、次のように入力します。

```
/review-loop:review-loop
```

これだけです。review-loopはチェックを実行し、変更をレビューし、修正が必要なものを修正して、残りについてユーザーに確認します。最後に、このリポジトリでコミットゲートを有効にするかどうかを1回だけ確認し、その後でコミットするかどうかを確認します。

初めての方は[ガイド](../../docs/guide/README.md)(英語)をご覧ください。最初のレビュー、判断のしかた、コミットゲート、コスト、つまずきやすい点を、実際の出力とともに説明しています。

## 使い方

### `/review-loop:review-loop`を使うだけ

コミットしようとするときに、いつでも入力します。コマンドの後に、やってほしいことを普通の文章で付け加えられます。

```
/review-loop:review-loop I changed the coupon math. Check it before I commit.
```

```
/review-loop:review-loop confirm every P2 with me before you fix anything.
```

ユーザーがレビューやコミットを頼んだときに、Claudeが自分でreview-loopを開始することもあります。ただし、Claudeがこのスキルが合うと判断した場合に限ります。コマンドを使えば、必ず開始します。

### 1ラウンドの流れ

すべてのラウンドはレポートで終わります。Claudeは何よりも先にレポートを表示します。

```
Review round 2 of 3 (reviewer: session model)
Checks: test (npm run test) passed

Resolved since last round:
- F-1 [P1] Coupon total adds the discounted sum on top of the full subtotal (fixed, inferred: the re-review read the fix)
  test: src/coupon.test.js (before the fix: caught, after: passed)

Trend (P1 + P2): 1 -> 0
Stopped: no P1 or P2 left in this change
Left for you: P3 1, P4 0, P5 0
```

この例では、ラウンド1でP1が1件見つかりました。Claudeはそれを修正して回帰テストを書き、review-loopはそのテストが修正前のコードで失敗することを示しました。ラウンド2で修正が確認されたため、ループは停止しました。P3が1件、ユーザーの判断に残っています。

## レビューの流れ

コミットの前に、review-loopは短いループを実行し、自分で停止します。

1. **チェック。** プロジェクトが宣言している`typecheck`、`lint`、`test`のチェックを実行します。対象は`package.json`のスクリプト、Makefileのターゲット、Go(`go.mod`)とRust(`Cargo.toml`)の標準コマンド、設定済みのPythonツール、Gradle、Maven、.NET、使っているRubyツールです。チェックが失敗した場合、または`package.json`が正しいJSONでない場合は、P1の指摘になります。チェックが制限時間を超えた場合、またはそのプログラムがインストールされていない場合は、失敗ではなく「未検証」(not verified)として報告します。
2. **新しいレビュー。** 別のレビュアーエージェントは、diffと、ユーザーが望んだ内容の1行の要約を受け取ります。この変更についてのClaudeの推論は受け取りません。文脈を理解するために、周辺のコードを読むことはできます。レビュアーは指摘にP1からP5のラベルを付けます。P1とP2には根拠が必要です。根拠とは、該当する行、失敗するシナリオ、既存の仕組みがその失敗を防げない理由です。各指摘にはmeasured(測定)、inferred(推論)、guessed(推測)のいずれかのラベルが付きます。根拠のないP1やP2、またはguessedのP1やP2は修正せず、検証されていない指摘としてユーザーに表示します。
3. **修正。** Claudeは何を修正するかを先に伝え、その後でP1とP2を修正します。修正に設計上の選択が必要な場合(修正方法が複数ある、目に見える動作が変わる、機能を削除する、テストを変更する)は、先にユーザーが選びます。プロジェクトにtestスクリプトがある場合、Claudeは修正するP1とP2ごとに、失敗シナリオから回帰テストを書きます。review-loopは、そのテストが修正前のコードで失敗することを示します。
4. **再レビュー。** 新しいレビュアーが、修正箇所とまだ解決していない指摘だけを確認します。最大3ラウンドです。
5. **停止。** 停止のタイミングは、モデルではなくスクリプトが決めます。スクリプトは次のいずれかに当てはまると停止します：P1とP2が残っていない、ラウンドの上限に達した、2回修正しても残る指摘がある、解決済みの指摘が再び現れた、P1 + P2の数が減らなくなった、修正がテストやチェックを弱めた。
6. **判断。** 残りは、ユーザーが1回だけ判断します。対象は、すべてのP3からP5と、まだ解決していないか、検証できなかったか、レビューしたdiffの外のファイルに関するP1とP2です。ユーザーは指摘ごとに、そのまま残す、今回だけ修正する、ルールにする、の3つから選びます。そのまま残した指摘は、引用した行が変わるまで、次回以降のレビューで再び確認されず、代わりにレポートで件数が示されます。このリポジトリの過去のレビューで、レビュアーが探す4種類のどれか(推測によるガードなど)が3回以上出ている場合、Claudeはそのことを伝え、当てはまる最も強い層でルールにするよう勧めます。順番は、型またはアーキテクチャの変更、lintルール、テストです。
7. **コミット。** ユーザーが「このリポジトリでは今後確認しない」を選んでいなければ、Claudeはコミット前に確認します。pushは一切行いません。コミットゲートを有効にすると、hookがこの動作をルールにします。レビューに合格するまで、Claudeのコミットはブロックされます。

Claudeは何かを修正したと言うとき、それをどう確かめたかも伝えます。合格するようになったチェックはmeasured、新しいコードを読んで判断したものはinferredです。ユーザーが指摘に反論すると、Claudeは同意する前にその主張をもう一度確かめ、何を確かめたかを伝えます。

### レビュアーが探すもの

レビュアーは、バグ、要件の欠落、プロジェクトルールの違反、そのほか、ユーザーが望んだことを変更が実現できなくなる問題を探します。ユーザーが望んだこと自体には異を唱えません。さらに、問題の原因が分からないときにエージェントが追加しがちな4種類のコードも探します。次のエージェントがそれを真似するからです。

<details>
<summary>4つの種類</summary>

| 種類 | 内容 | 重大度 |
|---|---|---|
| 推測によるガード | 起こりうるという根拠がない状態に対するチェック、try/catch、フォールバック、デフォルト値 | 失敗を隠す場合はP2、それ以外はP3 |
| 経緯コメント | 誰が何を頼んだか、以前のバージョンがなぜ変わったかを書いたコメント、またはエージェントへの指示 | P4 |
| 手抜きの目印 | IssueへのリンクがないTODO、HACK、「temporary」、「for now」のコメント | P3 |
| 2つ目のやり方 | コードベースがすでに別の方法で行っている処理のためのヘルパー、パターン、依存関係 | P3 |

ガードが正しいのは、正当な状態がコードに入ってくる場所です。たとえば、ユーザー入力、ネットワークやファイルの読み込み、APIが欠けることがあると明記している値です。すでに処理済みの状態に対して、さらに内側でもう一度チェックするのは、やはり推測によるガードです。[`evals/review-loop/fixtures/reviewer-rubric/`](../../evals/review-loop/fixtures/reviewer-rubric/)のfixtureには各種類が1つずつ含まれており、レビュアーがそれらを指摘することを確認します。

</details>

### 重大度

Banksaladが公開しているPnルールに基づきます。

| レベル | 意味 | ループの動作 |
|---|---|---|
| P1 | 必ず修正：チェックの失敗、データ損失、セキュリティホール、クラッシュ、または要求された機能が動かない | 根拠がある場合だけ修正 |
| P2 | 修正すべき：特定の入力で再現するバグ、要件の欠落、プロジェクトルールの違反 | 根拠がある場合だけ修正 |
| P3 | 修正する価値あり：保守性、誤解を招く名前、重要度の低い経路のテスト不足 | ユーザーが判断 |
| P4 | 任意：人によって意見が分かれる構造の好み | ユーザーが判断 |
| P5 | 些細：タイプミスやフォーマット | ユーザーが判断 |

そのラウンドがレビューしたdiffにないファイルに関するP1やP2は、ループの中では修正しません。最後に「レビューしたdiffの外」と示してユーザーに渡し、重大度はそのまま残します。

### ルールと回帰テスト

レビュアーが繰り返し書かなければならないコメントは、ルールが足りていない証拠です。review-loopはその回数を数えます。各レビューは、すべての指摘の種類を、リポジトリのすべてのworktreeで共有するファイルに記録します。上の4種類のどれかに当たる指摘のうち、過去のレビューで同じ種類が3回以上出ているものには、繰り返しの印が付きます。correctnessのような広いラベルも記録されますが、繰り返しには数えません。ある指摘に「ルールにする」を選ぶと、Claudeはまず、その指摘を検出できたはずの既存のルールがlint設定やテストにないかを探します。次に、使える最初の形を選びます：既存のlintルールを有効にする、すでに使っているlinterのカスタムルールを書く、テストを書く。下書きは、指摘の対象となったファイルには決して書きません。

次に、review-loopは下書きを証明します。修正前のコードを一時フォルダーに書き出し、そこで下書きありと下書きなしの両方でチェックを実行します。

| 結果 | 意味 |
|---|---|
| `caught` | 下書きがあるときだけチェックが失敗する。ルールが間違いを検出できている |
| `missed` | 下書きがあってもすべてのチェックが通る。Claudeが1回だけ書き直す |
| `unproven` | チェックがタイムアウトした、または下書きなしでも失敗する。どちらなのかをClaudeが伝える |

ルールには、それを実行するチェックが必要です。`typecheck`、`lint`、`test`のどのスクリプトもない場合、選択は「今回だけ修正する」として記録され、Claudeがその理由を伝えます。証明された下書きは修正と同じコミットに入り、コミットメッセージにその名前が書かれます。

プロジェクトにtestスクリプトがある場合、Claudeが修正する各P1とP2には、確認なしで同じ方法で回帰テストが付きます。回帰テストでは、testチェックだけが証明として扱われます。テストを加えてもlintしか失敗しないなら、そのテストはバグを検出していません。テストのない修正は、その理由をレポートに書きます。

### コミットゲート

コミットゲートはhookです。このhookは、ユーザーがリポジトリで有効にするまでオフです。レビューの最後に、Claudeはこのhookを有効にするかどうかを1回だけ確認します。ゲートが有効な場合、Claudeが実行するすべての`git commit`を、ゲートが先にチェックします。

<details>
<summary>ゲートの動作</summary>

| 状況 | ゲートの動作 |
|---|---|
| レビューがない、またはレビューの対象外のファイルが変更された | コミットをブロックし、レビューを実行するようClaudeに伝える |
| レビューループの実行中、または未決定の項目が残っている | コミットをブロックする |
| レビューに合格した | コミット前にユーザーに確認する。ユーザーがこのリポジトリでコミットを委任している場合は、コミットを許可する |
| レビュー後に、レビュー済みのファイル、または`loop rule`が確認したルールの下書きと回帰テストだけが変更された | ユーザーに確認する |
| `git push`、force push | コミットを委任していても、必ず確認する |
| `--no-verify`を付けたコミット | コミットを委任していても確認する。レビューに合格していないコミットは引き続きブロックする |
| ゲートが読み取れないフォルダーでのコミット(例: `cd "$(...)"`、存在しないパス) | Claude Codeを起動したリポジトリでゲートがオンなら、コミットを委任していても確認する |

レビューなしで1回だけコミットするには、今回はレビューを省略するようClaudeに頼みます。ゲートの設定とコミットの委任は、リンクされたworktreeを含むリポジトリ全体に適用されます。レビューはworktreeごとに別です。

</details>

### 設定

最初の5つの設定は1つのリポジトリに適用されます。設定を変更するには、`/review-loop:review-loop`の後に要望を入力します。そうすると、Claudeはスキルのコマンドを読み込んだ状態で変更できます。チェックの制限時間は環境変数なので、設定した場所であればどこでも適用されます。合計9分は固定です。

| 設定 | デフォルト | 入力する内容 |
|---|---|---|
| 修正前の確認 | オフ | 「P2はすべて先に確認して」または「P1とP2はすべて先に確認して」 |
| コミットゲート | 最初のレビューの最後に1回だけ確認 | 「コミットゲートを有効にして(または無効にして)」 |
| コミットの委任 | コミットのたびに確認 | 「このリポジトリではコミット前に確認しないで」 |
| 無人実行 | オフ | 1回だけなら「無人で実行して」、このリポジトリで続けるなら「このリポジトリで無人モードを有効にして(または無効にして)」。Claudeは何も質問せず、ユーザーの判断が必要なことは後回しにし、最後に行ったことと対応を待っていることをまとめて報告します |
| レビュアーのモデル | セッションのモデル | 「このリポジトリではレビュアーをsonnetで実行して」(またはopus、haiku、fable)、または「レビュアーをセッションのモデルで実行して」。各モデルが見つけたものとコストは測定結果にあります |
| チェックの制限時間 | チェックごとに5分、合計9分 | チェックごとの制限時間を変えるには`LIM_CHECK_TIMEOUT_MS`を設定 |

## 測定結果

## この仕組みにした理由

<details>
<summary>なぜ新しいレビュアーなのか</summary>

変更を書いたエージェントは、すべての行がなぜそこにあるかを知っているので、変更を正しいものとして読んでしまいます。diffと1行の意図だけを受け取ったレビュアーは、その理由をコードの中から見つけなければなりません。理由がコードになければ、それが指摘になります。ラウンドごとに新しいレビュアーを起動するので、レビュアーが自分の以前の判定を採点することはありません。

</details>

<details>
<summary>なぜスクリプトが停止を決めるのか</summary>

「これで完了？」と聞かれたモデルは、はいと答えがちです。review-loopのスクリプトは、代わりに数を数えます。P1とP2が残っていないとき、3ラウンドを終えたとき、2回修正しても指摘が残るとき、解決済みの指摘が再び現れたとき、P1 + P2が減らなくなったとき、修正がテストを弱めたときに停止します。未解決の指摘を残したまま停止するのは普通の結果であり、Claudeはそのことをはっきり伝えます。

</details>

<details>
<summary>なぜP1とP2には根拠が必要なのか</summary>

自信のある主張と証明された主張は、レポートの上では同じに見えます。P1とP2は、該当する行をそのまま引用し、誤った結果を生む入力を示し、既存の仕組みがそれを防げない理由を述べなければなりません。3つのうち1つでも欠けている場合、またはレビュアーがguessedのラベルを付けた場合、その指摘は検証されていない指摘として表示され、Claudeはそのためにコードを変更しません。

</details>

<details>
<summary>なぜコミットゲートはオプトインなのか</summary>

コミットをブロックするhookは、作業のやり方を変えます。そのため、リポジトリごとにユーザーが選ぶべきです。ゲートがなければ、「コミット前に確認する」はClaudeが従う指示にすぎません。ゲートがあれば、レビューに合格しないままClaudeが実行する`git commit`をhookがブロックします。ただし、hookはすべてを検知できるわけではありません。ユーザーが自分のターミナルで入力したコミットなど、検知できないものは[制限事項](#制限事項)にまとめています。

</details>

<details>
<summary>なぜpushしないのか</summary>

コミットはローカルにあり、簡単に取り消せます。pushはそうではありません。review-loopはコミットで止まり、ユーザーがコミットを委任していても、ゲートはpushのたびに確認します。

</details>

## データ

状態、diff、チェックのログ、判断の記録(decision ledger)は、リポジトリ内の`.git/lim/review-loop/`に保存されます。Claudeは各レビューを作業ツリーの`.lim-review/`に一時的に書き込みます。gitは`.git/info/exclude`によってこのフォルダーを無視し、review-loopはファイルを読み込んだ後に削除します。ルールを確認するとき、review-loopは修正前のコードをリポジトリ外の一時フォルダーに書き込み、終わったら削除します。リセットするには、`.git/lim/review-loop/`を削除します。

review-loop自体はネットワーク通信を行いません。Claudeとレビュアーは、diff、指摘、チェックの出力を、セッション内の他のファイルと同じように読みます。そのため、これらの内容は、Claude Codeセッションの他の内容と同じように、モデルの提供元に送信されます。

## 制限事項

- チェックは`package.json`のスクリプト、Makefileのターゲット、Go、Rust、設定済みのPythonツール(pytest、ruff、mypy)、Gradle、Maven、.NET、プロジェクトが使っているRubyツール(rspec、rake test、rubocop)の順に、リポジトリのルートと、変更が触れたサブフォルダーのプロジェクト(1ラウンドに最大4つ)から検出します。
- 各チェックは最大5分、すべてのチェックの合計は最大9分です。
- コミットゲートが無効の場合、コミット前の確認はClaudeへの指示であり、保証ではありません。
- コミットゲートがチェックするのは、ClaudeがBashツールで実行するコマンドだけです。ユーザーが自分のターミナルで入力したコミットはチェックしません。`git ci`のようなgitのエイリアスを通したコミットは、`git commit`と同じようにチェックします。コミットするシェルエイリアス(`!...`)は、ゲートが中身を見られないため確認を求めます。`git -c alias.ci=commit`のようにその場で設定したエイリアスは認識しません。
- リポジトリではないフォルダーでClaude Codeを起動した場合、ゲートはリポジトリを特定できないコミットをチェックできません。例: `cd "$(...)"`の後のコミット。
- レビュー対象は、`git add -A`が含めるすべての変更です。手動で選んでステージした変更だけをレビューするわけではありません。
- ルールと回帰テストは一時的なコピーで確認します。このコピーには、追跡対象のファイルと、ルートおよび指摘と下書きがあるプロジェクトの`node_modules`へのリンクが含まれます。`.env`など、その他の無視されたファイルは含まれません。そのため、それらが必要なチェックでは、ルールやテストが未証明、または誤った理由で検出されたと報告されます。どちらなのかは、Claudeが失敗の内容を読んで判断します。

## FAQ

**review-loopは自動で開始しますか？**
常に開始するわけではありません。Claudeは、スキルの説明が会話に合うと判断した場合にだけ、そのスキルを開始します。ユーザーがClaudeにレビューやコミットを頼むと、Claudeがreview-loopを開始する場合がありますが、開始する保証はありません。`/review-loop:review-loop`コマンドを使うと、必ずreview-loopが開始します。ユーザーがコミットゲートを有効にすると、レビューのないコミットはブロックされます。そのとき、Claudeは先にreview-loopを実行するよう指示を受けます。

**pushやmergeをしますか？**
一切しません。ユーザーが「このリポジトリでは今後確認しない」を選んでいなければ、すべてのコミットの前に確認します。この設定を元に戻すには、review-loopのコミット委任をオフにするようClaudeに頼みます。

**他のプラグインと競合しますか？**
review-loopが追加するのは、スキル1つ、エージェント1つ、hook1つです。このhookはBashコマンドを読み、`git commit`と`git push`にだけ反応します。ユーザーがそのリポジトリでコミットゲートを有効にしていなければ、このhookは何もしません。名前はすべて`review-loop:`で始まるため、他のプラグインの名前と衝突しません。ユーザーが普通の文章で頼んだ場合は、Claudeが別のレビュースキルを選ぶ場合があります。コマンドを使えば、必ずreview-loopが開始します。

**ループの途中でセッションが終了した場合はどうなりますか？**
コマンドをもう一度実行します。コマンドは、停止したラウンドとステップから続けるか、最初からやり直すかを提案します。

**アンインストールするには？**

```
claude plugin uninstall review-loop@lim
claude plugin marketplace remove lim
```

その後、review-loopを実行した各リポジトリで`.git/lim/review-loop/`と、`.git/info/exclude`の`.lim-review/`の行を削除します。

## 自分のものにする

review-loopは、プロジェクトにすでにあるチェックを使って動きます。`typecheck`、`lint`、`test`スクリプトが充実しているほど、レビューのうち、読んで判断する部分が減り、測定で確かめる部分が増えます。

- 何かが変わる前に重大な指摘を見たい場合は、すべてのP2、またはすべてのP1とP2を先に確認するようClaudeに頼みます。
- 信頼しているリポジトリでコミットを毎回承認するのが面倒な場合は、そのリポジトリでコミットを委任します。コミットゲートが有効なら、pushについては引き続き確認されます。
- 同じコメントを何度も受ける場合は、「ルールにする」を選びます。次のレビューからは、その間違いをプロジェクトのlinterやテストが最初から検出します。
- 別の流れにしたい場合は、プラグインをフォークします。スキルは250行未満の`SKILL.md`1つで、ループのロジックは`plugins/review-loop/skills/review-loop/scripts/loop.mjs`という1つのスクリプトです。

## LIMの作り方

- **まずIssueから。** すべての変更はIssueから始まります。変更はpull requestを通じて取り込まれ、メンテナーがそのpull requestをsquash mergeします。
- **自分自身でレビュー。** すべてのpull requestで、そのdiffに対してreview-loopを実行します。説明欄には、レポートと指摘ごとの判断を載せます。
- **プラグインごとのバージョン。** 各プラグインはSemantic Versioningに従い、独自の`CHANGELOG.md`を持ち、`<plugin>--v<version>`の形式でタグを付けます。マイナーリリースとメジャーリリースでは、GitHub Releaseを作成します。
- **意図的に小さく。** 1つのプラグインが持つのは、エントリースキル1つ、250行未満の`SKILL.md`、オプトインのhookだけです。
