Агенты для программирования пишут код быстро. Замечать собственные ошибки у них получается намного хуже. Агент, который написал изменение, проверяет его хуже всех: он читает изменение через собственные рассуждения и соглашается сам с собой. Поэтому работу коммитят без ревью или с ревью из того же контекста, в котором её написали.

**Мой ответ на это называется LIM: небольшие плагины, каждый из которых выполняет одну задачу и подкреплён цифрами.** Первый из них называется review-loop.

**С review-loop «готово к коммиту» означает «прошло ревью».** Сначала запускаются ваши собственные тесты, проверка типов и lint. Затем ревьюер с чистым контекстом, который никогда не видит рассуждений Claude, присваивает замечаниям уровни от P1 до P5 и для серьёзных замечаний обязан привести доказательства. Claude исправляет P1 и P2, новый ревьюер проверяет исправления, а момент остановки определяет скрипт, а не модель. Об остальном вы решаете один раз, в конце.

**Замечания, которые вы повторяете снова и снова, становятся правилами.** Когда вы отмечаете замечание как «сделать правилом», Claude пишет черновик lint-правила или теста, а review-loop запускает его на коде до исправления, чтобы доказать, что он ловит ошибку. Исправление бага таким же образом получает регрессионный тест.

**Небольшой размер намеренно.** review-loop добавляет к сессии около 212 токенов. Его хук ничего не делает, пока вы не включите его в репозитории. Ничего не устанавливается без объяснения, что это и как это удалить.

Сделайте форк, измените, подстройте под себя. Мы принимаем issue и pull request.

## Установка

Вам нужны Claude Code, git и Node.js 18 или новее.

```
/plugin marketplace add lee-eojin/lim
/plugin install review-loop@lim
```

Если Claude Code попросит перезапуск, перезапустите его. Добавление marketplace только регистрирует каталог плагинов. Каждый плагин устанавливается отдельно, поэтому вы получаете только то, что выбрали.

## Начало работы

Два шага:

1. Установите review-loop, как описано выше.
2. В git-репозитории с незакоммиченными изменениями введите:

```
/review-loop:review-loop
```

Вот и всё. review-loop запускает ваши проверки, проводит ревью изменения, исправляет то, что нужно исправить, и спрашивает вас об остальном. В конце он один раз спрашивает, включить ли commit gate для этого репозитория, а затем, делать ли коммит.

## Использование

### Просто используйте `/review-loop:review-loop`

Вводите команду каждый раз, когда собираетесь сделать коммит. После команды можно обычными словами добавить, чего вы хотите:

```
/review-loop:review-loop I changed the coupon math. Check it before I commit.
```

```
/review-loop:review-loop confirm every P2 with me before you fix anything.
```

Claude может запустить review-loop и сам, когда вы просите провести ревью или сделать коммит, но только если решит, что этот skill подходит. Команда запускает review-loop всегда.

### Как выглядит раунд

Каждый раунд заканчивается отчётом. Claude показывает его раньше всего остального:

```
Review round 2 of 3
Checks: test passed

Resolved since last round:
- F-1 [P1] Coupon total adds the discounted sum on top of the full subtotal (fixed, inferred: the re-review read the fix)
  test: src/coupon.test.js (before the fix: caught, after: passed)

Trend (P1 + P2): 1 -> 0
Stopped: no P1 or P2 left in this change
Left for you: P3 1, P4 0, P5 0
```

Здесь в первом раунде нашлось замечание P1. Claude исправил его и написал регрессионный тест, а review-loop показал, что тест падает на коде до исправления. Второй раунд подтвердил исправление, и цикл остановился. Одно замечание P3 осталось на ваше решение.

### Примеры


## Как проходит ревью

Перед коммитом review-loop запускает короткий цикл и сам останавливается.

1. **Проверки.** review-loop запускает скрипты `typecheck`, `lint` и `test` из вашего `package.json`. Если проверка не проходит или `package.json` не является корректным JSON, это становится замечанием P1. Если проверка превышает лимит времени, она отмечается как «не проверено», а не как непройденная.
2. **Новое ревью.** Отдельный агент-ревьюер получает diff и однострочное описание вашей цели, но не получает рассуждения Claude об этом изменении. Ревьюер может читать окружающий код, чтобы понять контекст. Он присваивает замечаниям уровни от P1 до P5. Для P1 и P2 нужны доказательства: точная строка, сценарий сбоя и объяснение, почему существующий код это не предотвращает. Каждое замечание помечается как measured (измерено), inferred (выведено из кода) или guessed (предположение). Замечание P1 или P2 без доказательств или с пометкой guessed показывается вам как непроверенное и не исправляется.
3. **Исправление.** Claude сообщает, что он исправит, и затем исправляет P1 и P2. Если исправление требует решения по дизайну (больше одного способа исправить, видимое изменение поведения, удаление функции, изменение тестов), сначала выбираете вы. Если в проекте есть скрипт test, Claude пишет регрессионный тест по сценарию сбоя каждого исправленного P1 или P2, а review-loop показывает, что тест падает на коде до исправления.
4. **Повторное ревью.** Новый ревьюер проверяет только исправления и ещё открытые замечания. Максимум 3 раунда.
5. **Остановка.** Решение об остановке принимает скрипт, а не модель. Условия остановки: не осталось P1 и P2, достигнут лимит раундов, замечание осталось после двух исправлений, решённое замечание вернулось, сумма P1 + P2 перестала уменьшаться или исправление ослабило тесты или проверки.
6. **Решение.** Вы один раз решаете, что делать с остальными замечаниями: со всеми замечаниями от P3 до P5 и с каждым замечанием P1 или P2, которое ещё открыто, которое не удалось проверить или которое относится к файлу вне проверенного diff. Для каждого замечания вы выбираете: оставить как есть, исправить только в этот раз или сделать правилом. О замечании, которое вы оставили как есть, в следующем ревью не спрашивают повторно, пока не изменится процитированная строка, а отчёт вместо этого учитывает его в общем числе. Если прошлые ревью в этом репозитории уже 3 раза или больше находили один из четырёх видов, которые ищет ревьюер (например, защитную проверку на всякий случай), Claude говорит об этом и советует сделать его правилом на самом сильном подходящем уровне: сначала изменение типов или архитектуры, затем lint-правило, затем тест.
7. **Коммит.** Если вы не выбрали «больше не спрашивать в этом репозитории», Claude спрашивает вас перед коммитом. Он никогда не делает push. Если вы включите commit gate, хук сделает это правилом: коммиты Claude блокируются, пока ревью не завершится успешно.

Когда Claude говорит, что что-то исправлено, он объясняет, откуда это известно: проверка, которая теперь проходит, считается measured, а его прочтение нового кода считается inferred. Когда вы оспариваете замечание, Claude перед тем, как согласиться, ещё раз проверяет утверждение и рассказывает, что именно он проверил.

### Что ищет ревьюер

Ревьюер ищет баги, невыполненные требования, нарушенные правила проекта и всё остальное, из-за чего изменение не достигнет того, чего вы хотели. Саму вашу цель он не оспаривает. Ещё он ищет четыре вида кода, который агенты добавляют, когда не знают причины проблемы, потому что следующий агент копирует такой код:

<details>
<summary>Четыре вида</summary>

| Вид | Что это | Уровень |
|---|---|---|
| Защитная проверка на всякий случай | Проверка, try/catch, запасной вариант или значение по умолчанию для состояния, возможность которого ничем не подтверждена | P2, если она скрывает сбой, иначе P3 |
| Комментарий об истории | Комментарий о том, кто что просил, почему изменилась прежняя версия, или инструкция для агентов | P4 |
| Пометка о временном решении | Комментарий TODO, HACK, «temporary» или «for now» без ссылки на issue | P3 |
| Второй способ | Вспомогательная функция, паттерн или зависимость для задачи, которую кодовая база уже решает иначе | P3 |

Защитная проверка уместна там, где в код попадает законное состояние: пользовательский ввод, чтение из сети или файла или значение, которое по документации API может отсутствовать. Вторая проверка глубже в коде для состояния, которое уже обработано, всё равно остаётся проверкой на всякий случай. Fixture в [`evals/review-loop/fixtures/reviewer-rubric/`](../../evals/review-loop/fixtures/reviewer-rubric/) содержит по одному примеру каждого вида и проверяет, что ревьюер их отмечает.

</details>

### Уровни серьёзности

Уровни основаны на публичном правиле Pn компании Banksalad.

| Уровень | Значение | Поведение цикла |
|---|---|---|
| P1 | Обязательно исправить: проверка не проходит, потеря данных, уязвимость безопасности, аварийное завершение (crash) или запрошенная функция не работает | Исправляется, если есть доказательства |
| P2 | Следует исправить: баг, который воспроизводится на конкретном вводе, невыполненное требование, нарушенное правило проекта | Исправляется, если есть доказательства |
| P3 | Стоит исправить: сопровождаемость, вводящее в заблуждение имя, отсутствие теста на второстепенном пути | Решаете вы |
| P4 | Необязательно: структурное предпочтение, о котором мнения расходятся | Решаете вы |
| P5 | Мелочь: опечатка или форматирование | Решаете вы |

Замечание P1 или P2 о файле, которого нет в diff, проверенном в раунде, в цикле не исправляется. Оно приходит к вам в конце с пометкой «вне проверенного diff» и сохраняет свой уровень серьёзности.

### Правила и регрессионные тесты

Замечание, которое ревьюеру приходится повторять, означает, что не хватает правила. review-loop ведёт счёт: каждое ревью записывает вид каждого замечания в файл, общий для всех worktree репозитория, и замечание одного из четырёх видов выше, вид которого прошлые ревью находили уже 3 раза или больше, помечается как повторное. Широкие метки вроде correctness записываются, но никогда не считаются повтором. Когда вы выбираете для замечания «сделать правилом», Claude сначала ищет в вашей конфигурации lint или в тестах существующее правило, которое должно было это поймать. Затем он выбирает первый подходящий вариант: включить существующее lint-правило, написать своё правило для линтера, который вы уже используете, или написать тест. Черновик никогда не попадает в файл, к которому относится замечание.

Затем review-loop доказывает, что черновик работает. Он записывает код до исправления во временную папку и запускает там ваши проверки с черновиком и без него:

| Результат | Значение |
|---|---|
| `caught` | Проверка падает только с черновиком. Правило ловит ошибку. |
| `missed` | С черновиком все проверки проходят. Claude один раз дорабатывает его. |
| `unproven` | Проверка превысила лимит времени или падает и без черновика. Claude сообщает, какой из этих случаев произошёл. |

Правилу нужна проверка, которая будет его запускать. Если нет скрипта `typecheck`, `lint` или `test`, выбор записывается как «исправить только в этот раз», и Claude объясняет почему. Доказанный черновик попадает в тот же коммит, что и исправление, и сообщение коммита его упоминает.

Каждое замечание P1 или P2, которое исправляет Claude, таким же образом и без вопросов получает регрессионный тест, если в проекте есть скрипт test. Для регрессионного теста доказательством считается только проверка test: если с ним падает только lint, тест не поймал баг. Если исправление осталось без теста, отчёт объясняет почему.

### Commit gate

Commit gate представляет собой хук, который выключен, пока вы не включите его в репозитории. В конце ревью Claude один раз спрашивает, включить ли его. Когда commit gate включён, каждый `git commit`, который запускает Claude, сначала проходит проверку.

<details>
<summary>Что делает commit gate</summary>

| Ситуация | Что делает commit gate |
|---|---|
| Ревью не было, или изменились файлы, которые ревью не охватило | Блокирует коммит и говорит Claude запустить ревью |
| Цикл ревью ещё идёт, или решения ещё не приняты | Блокирует коммит |
| Ревью завершилось успешно | Спрашивает вас перед коммитом или разрешает коммит, если вы делегировали коммиты в этом репозитории |
| После ревью изменились только проверенные файлы или черновики правил и регрессионные тесты, проверенные `loop rule` | Спрашивает вас |
| `git push` или force push | Всегда спрашивает, даже при делегировании |
| Коммит с `--no-verify` | Спрашивает, даже при делегировании, и по-прежнему блокирует коммит без успешного ревью |
| Коммит в папке, которую gate не может определить, например `cd "$(...)"` или несуществующий путь | Спрашивает вас, даже при делегировании, если gate включён в репозитории, где вы запустили Claude Code |

Чтобы один раз сделать коммит без ревью, попросите Claude пропустить ревью в этот раз. Настройка gate и делегирование коммитов действуют для всего репозитория, включая связанные worktree. У каждого worktree своё ревью.

</details>

### Настройки

Первые четыре настройки действуют для одного репозитория. Чтобы изменить настройку, введите запрос после `/review-loop:review-loop`, тогда у Claude будут загружены команды этого skill. Лимит времени проверок задаётся переменной окружения, поэтому он действует везде, где вы её задали, а общий лимит в 9 минут фиксирован.

| Настройка | По умолчанию | Что ввести |
|---|---|---|
| Подтверждение перед исправлением | Выключено | «согласовывай со мной каждое P2» или «согласовывай со мной каждое P1 и P2» |
| Commit gate | Вопрос задаётся один раз в конце первого ревью | «включи (или выключи) commit gate» |
| Делегирование коммитов | Вопрос перед каждым коммитом | «больше не спрашивай перед коммитами в этом репозитории» |
| Автономный режим | Выключено | «работай автономно» для одного запуска или «включи (или выключи) автономный режим в этом репозитории». Claude ничего не спрашивает, откладывает на потом то, что требует вашего участия, и в конце выдаёт сводку того, что сделано и что ждёт вас |
| Лимит времени проверок | 5 минут на одну проверку, 9 минут на все вместе | Чтобы изменить лимит для одной проверки, задайте `LIM_CHECK_TIMEOUT_MS` |

## Измерения

[`evals/review-loop/behaviors.csv`](../../evals/review-loop/behaviors.csv) содержит 149 вариантов поведения по шести осям: do (делать), tell (сообщать), ask (спрашивать), silence (молчать), stop (останавливаться) и evidence (доказательства). Модульные тесты в CI покрывают 139 из них, включая запуски на реальных временных git-репозиториях и проверки хука commit gate. Остальные 10 требуют запуска модели: один вопрос о замечаниях от P3 до P5, показ отчёта до любого вопроса, сохранение каждого шага в списке задач с причиной для каждого пропуска, регрессионный тест для каждого исправленного P1 или P2, пометка каждого замечания как measured, inferred или guessed, объяснение, откуда известно, что исправление работает, повторная проверка замечания, когда вы его оспариваете, совет сделать правилом вид замечаний, который повторяется снова и снова, отсутствие вопросов в автономном запуске и сообщение о коде, добавленном без известной причины. Для последнего варианта есть fixture в [`evals/review-loop/fixtures/reviewer-rubric/`](../../evals/review-loop/fixtures/reviewer-rubric/), а для первых двух есть ручной прогон в [`evals/review-loop/manual-behaviors.md`](../../evals/review-loop/manual-behaviors.md).

Бенчмарк обнаружения в [`evals/review-loop/detection/`](../../evals/review-loop/detection/) даёт ревьюеру 12 изменений, в каждое из которых внесён один баг, и 6 чистых изменений. Они лежат во временных репозиториях, по названиям которых нельзя понять, что это тест. В прогоне 2026-10-25 с claude-opus-5-5, по 1 запуску на каждый случай, ревьюер отнёс все 12 багов к P1 или P2 и не выдал ни одного P1 или P2 на чистых изменениях. Прогон потратил около 390 000 токенов ($0.89) и занял 74 секунды, по 4 случая одновременно. Высший балл также означает, что эти случаи слишком просты, чтобы показать небольшую регрессию, поэтому дальше будут более сложные случаи. Запустить снова можно командой `node evals/review-loop/run-detection.mjs`.

<details>
<summary>Стоимость</summary>

По оценке `claude plugin details`, review-loop стоит:

| Часть | Всегда, в каждой сессии | При каждом запуске |
|---|---|---|
| skill review-loop | около 140 токенов | около 4600 токенов |
| агент-ревьюер | около 70 токенов | около 1700 токенов плюс diff и код, который он читает |

Стоимость skill оплачивается один раз за запуск. Стоимость ревьюера оплачивается один раз за раунд, а цикл проходит не больше 3 раундов. Ваши проверки работают на вашей машине и не тратят токены.

</details>

review-loop проводит ревью pull request самого LIM. [#8](https://github.com/lee-eojin/lim/pull/8) показывает два цикла на первой версии, в том числе остановку из-за ложного срабатывания в собственной проверке ослабления тестов. Эту ошибку затем исправили. Недавние pull request, например [#46](https://github.com/lee-eojin/lim/pull/46), показывают отчёт review-loop и решение по каждому замечанию.

## Почему это работает так

<details>
<summary>Зачем нужен новый ревьюер?</summary>

Агент, который написал изменение, знает, зачем нужна каждая строка, поэтому считает изменение правильным. Ревьюер, который получает только diff и одну строку о цели, должен найти причину в коде. Если причины там нет, это и есть замечание. Каждый раунд запускает нового ревьюера, поэтому ревьюер никогда не оценивает собственный прошлый вердикт.

</details>

<details>
<summary>Почему остановку определяет скрипт?</summary>

Модель, которую спрашивают «готово?», обычно отвечает «да». Скрипт review-loop вместо этого считает: он останавливает цикл, когда не осталось P1 и P2, после 3 раундов, когда замечание осталось после двух исправлений, когда решённое замечание вернулось, когда сумма P1 + P2 перестала уменьшаться или когда исправление ослабило тест. Остановка с открытыми замечаниями считается нормальным исходом, и Claude прямо об этом говорит.

</details>

<details>
<summary>Почему P1 и P2 нужны доказательства?</summary>

В отчёте уверенное утверждение и доказанное выглядят одинаково. Замечание P1 или P2 должно процитировать точную строку, назвать ввод, который даёт неверный результат, и объяснить, почему существующий код это не предотвращает. Если чего-то из этих трёх пунктов нет или ревьюер пометил замечание как guessed, оно показывается как непроверенное, и Claude не меняет из-за него код.

</details>

<details>
<summary>Почему commit gate включается только по вашему выбору?</summary>

Хук, который блокирует коммиты, меняет ваш способ работы, поэтому решать об этом нужно вам и для каждого репозитория отдельно. Без gate «спрашивать перед коммитом» остаётся инструкцией, которой следует Claude. С gate хук блокирует `git commit`, который Claude запускает без успешного ревью. Он видит не всё: в разделе [Ограничения](#ограничения) перечислено, что он пропускает, например алиасы git.

</details>

<details>
<summary>Почему он никогда не делает push?</summary>

Коммит локален, и его легко отменить. Push отменить не так просто. review-loop останавливается на коммите, а gate спрашивает перед каждым push, даже если вы делегировали коммиты.

</details>

## Данные

Состояние, diff, логи проверок и журнал решений хранятся в папке `.git/lim/review-loop/` внутри вашего репозитория. Claude ненадолго записывает каждое ревью в папку `.lim-review/` в вашем рабочем дереве; git игнорирует эту папку через `.git/info/exclude`, а review-loop удаляет файл после чтения. Чтобы проверить правило, review-loop записывает код до исправления во временную папку вне вашего репозитория и затем удаляет её. Чтобы сбросить состояние, удалите `.git/lim/review-loop/`.

review-loop сам не выполняет сетевых запросов. Claude и ревьюер читают diff, замечания и вывод проверок так же, как любой другой файл в вашей сессии. Поэтому это содержимое попадает к поставщику модели так же, как остальная часть вашей сессии Claude Code.

## Ограничения

- Проверки определяются только по скриптам в `package.json`.
- Каждая проверка может работать до 5 минут, а все проверки вместе до 9 минут.
- Без commit gate вопрос перед коммитом является инструкцией для Claude, а не гарантией.
- Commit gate проверяет только команды, которые Claude запускает через свой инструмент Bash. Коммиты, которые вы вводите в своём терминале, не проверяются, а алиасы git, например `git ci`, не распознаются.
- Если вы запускаете Claude Code в папке, которая не является репозиторием, gate не может проверить коммит, репозиторий которого он не может определить, например после `cd "$(...)"`.
- review-loop проводит ревью всего, что включил бы `git add -A`, а не набора staged-изменений, выбранного вручную.
- Правило или регрессионный тест проверяется во временной копии, в которой есть ваши отслеживаемые файлы и ссылка на корневой `node_modules`. Других игнорируемых файлов, например `.env` или вложенного `node_modules`, там нет, поэтому проверка, которой они нужны, сообщит, что результат не доказан или что ошибка поймана по неверной причине. Claude читает вывод ошибки, чтобы понять, какой из этих случаев произошёл.

## Частые вопросы (FAQ)

**review-loop запускается сам?**
Не всегда. Claude запускает skill только тогда, когда решает, что описание этого skill подходит к разговору. Если вы просите Claude провести ревью или сделать коммит, Claude может запустить review-loop, но это не гарантировано. Команда `/review-loop:review-loop` запускает review-loop всегда. Если вы включите commit gate, коммит без ревью будет заблокирован, и Claude получит указание сначала запустить review-loop.

**Делает ли он push или merge?**
Никогда. Если вы не выбрали «больше не спрашивать в этом репозитории», review-loop спрашивает перед каждым коммитом. Чтобы отменить этот выбор, попросите Claude отключить делегирование коммитов в review-loop.

**Будет ли он конфликтовать с другими моими плагинами?**
review-loop добавляет один skill, одного агента и один хук. Хук читает команды Bash, реагирует только на `git commit` и `git push` и ничего не делает, если вы не включили commit gate в этом репозитории. Его имена начинаются с `review-loop:`, поэтому они не могут совпасть с именами из других плагинов. Если вы формулируете запрос обычными словами, Claude может выбрать другой skill для ревью. Команда всегда запускает review-loop.

**Что произойдёт, если сессия закончится посреди цикла?**
Запустите команду снова. Она предложит продолжить с того раунда и шага, где цикл остановился, или начать заново.

**Как его удалить?**

```
claude plugin uninstall review-loop@lim
claude plugin marketplace remove lim
```

Затем удалите `.git/lim/review-loop/` в каждом репозитории, где вы запускали review-loop, и строку `.lim-review/` в его `.git/info/exclude`.

## Подстройте под себя

review-loop работает с теми проверками, которые у вас уже есть. Чем лучше ваши скрипты `typecheck`, `lint` и `test`, тем большая часть ревью измеряется, а не вычитывается.

- Хотите видеть серьёзные замечания до того, как что-то изменится? Попросите Claude согласовывать с вами каждое P2 или каждое P1 и P2.
- Надоело подтверждать коммиты в репозитории, которому вы доверяете? Делегируйте там коммиты. Если commit gate включён, перед push вопрос всё равно будет.
- Снова и снова пишете одно и то же замечание? Выберите «сделать правилом», и следующее ревью начнётся с того, что ваш собственный линтер или тесты уже ловят эту ошибку.
- Нужен другой порядок работы? Сделайте форк плагина. Skill состоит из одного файла `SKILL.md` короче 250 строк, а логика цикла находится в одном скрипте, `plugins/review-loop/skills/review-loop/scripts/loop.mjs`.

## Как устроена разработка LIM

- **Сначала issue.** Каждое изменение начинается с issue и попадает в проект через pull request. Мейнтейнер вливает этот pull request через squash merge.
- **Ревью собственным инструментом.** Каждый pull request запускает review-loop на своём diff, а в описании показаны отчёт и решение по каждому замечанию.
- **Отдельные версии для каждого плагина.** Каждый плагин следует Semantic Versioning, ведёт свой `CHANGELOG.md` и получает тег `<plugin>--v<version>`. Для minor и major релизов создаётся GitHub Release.
- **Небольшой размер намеренно.** У плагина один входной skill, `SKILL.md` короче 250 строк и только хуки, которые включаются по вашему выбору.
