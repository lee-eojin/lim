# LIM

**Less is more.** Небольшие плагины для Claude Code. Каждый плагин выполняет одну задачу и показывает измерения, на которых он основан.

## Почему LIM

Большие agent harness загружают много инструкций в каждую сессию и запускают хуки на многих командах. LIM делает каждый плагин небольшим, необязательным и измеренным.

- **Один плагин, одна задача.** Устанавливайте только то, что вам нужно. По данным `claude plugin details`, review-loop добавляет к сессии около 188 токенов.
- **Сначала проверки, потом мнения.** Ваши тесты, проверка типов и lint запускаются до любого ревью моделью.
- **Хуки включаются только по вашему выбору.** Хук ничего не делает, пока вы не включите его для репозитория.
- **Сначала вопрос, потом установка.** Плагин сначала объясняет всё, что ему нужно: что это, что это улучшает, где это хранится и как это удалить.
- **Цифры на виду.** Каждый плагин поставляется с описанием двух вещей: что измерено и что это измерение не покрывает.

## Плагины

| Плагин | Статус | Одна задача |
|---|---|---|
| [review-loop](../../plugins/review-loop) | 0.2.1 | Проводит ревью ваших изменений до коммита, исправляет замечания P1 и P2, проводит повторное ревью и передаёт остальные замечания вам. |
| forge | запланирован | Превращает комментарии ревьюера в pull request в skill ревьюера и добавляет отчёт о точности: насколько этот skill совпадает с самим ревьюером. |

## Быстрый старт

Вам нужны Claude Code, git и Node.js 18 или новее.

```
/plugin marketplace add lee-eojin/lim
/plugin install review-loop@lim
```

Если Claude Code попросит перезапуск, перезапустите его. Затем в git-репозитории с незакоммиченными изменениями выполните:

```
/review-loop:review-loop
```

Добавление marketplace только регистрирует каталог плагинов. Каждый плагин устанавливается отдельно, поэтому вы получаете только то, что выбрали.

## review-loop

Перед коммитом review-loop запускает короткий цикл и сам останавливается.

1. **Проверки.** review-loop запускает скрипты `typecheck`, `lint` и `test` из вашего `package.json`. Если проверка не проходит или `package.json` не является корректным JSON, review-loop создаёт замечание P1. Если проверка превышает лимит времени, review-loop отмечает её как «не проверено», а не как непройденную.
2. **Новое ревью.** Отдельный агент-ревьюер получает diff и однострочное описание вашей цели. Ревьюер не получает рассуждения Claude об этом изменении. Ревьюер может читать окружающий код, чтобы понять контекст. Ревьюер присваивает замечаниям уровни от P1 до P5. Для P1 и P2 нужны доказательства: точная строка, сценарий сбоя и объяснение, почему существующий код это не предотвращает. Утверждения без доказательств вы видите с пометкой «не проверено».
3. **Исправление.** Claude сообщает, что он исправит, и затем исправляет P1 и P2. Если исправление требует решения по дизайну (больше одного способа исправить, видимое изменение поведения, удаление функции, изменение тестов), сначала выбираете вы.
4. **Повторное ревью.** Новый ревьюер проверяет только исправления и ещё открытые замечания. Максимум 3 раунда.
5. **Остановка.** Решение об остановке принимает скрипт, а не модель. Условия остановки: не осталось P1 и P2, достигнут лимит раундов, замечание осталось после двух исправлений, решённое замечание вернулось, сумма P1 + P2 перестала уменьшаться или исправление ослабило тесты или проверки.
6. **Решение.** Вы один раз решаете, что делать с остальными замечаниями: со всеми замечаниями от P3 до P5 и с каждым замечанием P1 или P2, которое ещё открыто, не проверено или относится к файлу вне проверенного diff. Для каждого замечания вы выбираете: оставить как есть, исправить только в этот раз или сделать правилом.
7. **Коммит.** Если вы не выбрали «больше не спрашивать в этом репозитории», Claude спрашивает вас перед коммитом. review-loop никогда не делает push. Если вы включите commit gate, хук сделает это правилом: коммиты Claude блокируются, пока ревью не завершится успешно.

### Commit gate

Commit gate является хуком. Этот хук выключен, пока вы не включите его в репозитории. В конце ревью Claude один раз спрашивает, включить ли этот хук. Когда commit gate включён, он сначала проверяет каждый `git commit`, который запускает Claude:

| Ситуация | Что делает commit gate |
|---|---|
| Ревью не было, или изменились файлы, которые ревью не охватило | Блокирует коммит и говорит Claude запустить ревью |
| Цикл ревью ещё идёт, или решения ещё не приняты | Блокирует коммит |
| Ревью завершилось успешно | Спрашивает вас перед коммитом или разрешает коммит, если вы делегировали коммиты в этом репозитории |
| После ревью изменились только проверенные файлы | Спрашивает вас |
| `git push` или force push | Всегда спрашивает, даже при делегировании |
| Коммит с `--no-verify` | Спрашивает, даже при делегировании, и по-прежнему блокирует коммит без успешного ревью |
| Коммит в папке, которую gate не может определить, например `cd "$(...)"` или несуществующий путь | Спрашивает, даже при делегировании, если gate включён в репозитории, где вы запустили Claude Code |

Чтобы один раз сделать коммит без ревью, попросите Claude пропустить ревью в этот раз. Настройка gate и делегирование коммитов действуют для всего репозитория, включая связанные worktree. У каждого worktree своё ревью.

Каждый раунд заканчивается отчётом:

```
Review round 2 of 3
Checks: test passed

Resolved since last round:
- F-1 [P1] Coupon total adds the discounted sum on top of the full subtotal

Trend (P1 + P2): 1 -> 0
Stopped: no P1 or P2 left in this change
Left for you: P3 1, P4 0, P5 0
```

### Уровни серьёзности

Уровни основаны на публичном правиле Pn компании Banksalad.

| Уровень | Значение | Поведение цикла |
|---|---|---|
| P1 | Обязательно исправить: проверка не проходит, потеря данных, уязвимость безопасности, аварийное завершение (crash) или запрошенная функция не работает | Исправляется, только если есть доказательства |
| P2 | Следует исправить: баг, который воспроизводится на конкретном вводе, невыполненное требование, нарушенное правило проекта | Исправляется, только если есть доказательства |
| P3 | Стоит исправить: сопровождаемость, вводящее в заблуждение имя, отсутствие теста на второстепенном пути | Решаете вы |
| P4 | Необязательно: структурное предпочтение, о котором мнения расходятся | Решаете вы |
| P5 | Мелочь: опечатка или форматирование | Решаете вы |

Замечание P1 или P2 о файле, которого нет в diff, проверенном в раунде, в цикле не исправляется. Оно приходит к вам в конце с пометкой «вне проверенного diff» и сохраняет свой уровень серьёзности.

### Измерения

[`evals/review-loop/behaviors.csv`](../../evals/review-loop/behaviors.csv) содержит 68 вариантов поведения по шести осям: do (делать), tell (сообщать), ask (спрашивать), silence (молчать), stop (останавливаться) и evidence (доказательства). Модульные тесты в CI покрывают 66 из них, включая запуски на реальных временных git-репозиториях и проверки хука commit gate. Остальные 2 требуют запуска модели и запланированы для `claude plugin eval`: один вопрос о замечаниях от P3 до P5 и показ отчёта до любого вопроса.

review-loop проводит ревью pull request самого LIM. [#8](https://github.com/lee-eojin/lim/pull/8) показывает два цикла на первой версии review-loop. Один из циклов остановился из-за ложного срабатывания в собственной проверке ослабления тестов. Эту ошибку затем исправили.

### Данные

Состояние, diff, логи проверок и журнал решений хранятся в папке `.git/lim/review-loop/` внутри вашего репозитория. review-loop ничего не записывает в ваше рабочее дерево. Чтобы сбросить состояние, удалите эту папку.

review-loop сам не выполняет сетевых запросов. Claude и ревьюер читают diff, замечания и вывод проверок так же, как любой другой файл в вашей сессии. Поэтому это содержимое попадает к поставщику модели так же, как остальная часть вашей сессии Claude Code.

### Ограничения

- review-loop определяет проверки только по скриптам в `package.json`.
- Каждая проверка может работать до 5 минут, а все проверки вместе до 9 минут. Чтобы изменить лимит для одной проверки, задайте `LIM_CHECK_TIMEOUT_MS`.
- Без commit gate вопрос перед коммитом является инструкцией для Claude, а не гарантией.
- Commit gate проверяет только команды, которые Claude запускает через свой инструмент Bash. Коммиты, которые вы вводите в своём терминале, не проверяются. Алиасы git, например `git ci`, не распознаются.
- Если вы запускаете Claude Code в папке, которая не является репозиторием, gate не может проверить коммит, репозиторий которого он не может определить, например после `cd "$(...)"`.
- review-loop проводит ревью всего, что включил бы `git add -A`, а не набора staged-изменений, выбранного вручную.

## Частые вопросы (FAQ)

**review-loop запускается сам?**
Не всегда. Claude запускает skill только тогда, когда решает, что описание этого skill подходит к разговору. Если вы просите Claude провести ревью или сделать коммит, Claude может запустить review-loop, но это не гарантировано. Команда `/review-loop:review-loop` запускает review-loop всегда. Если вы включите commit gate, коммит без ревью будет заблокирован. Тогда Claude получит указание сначала запустить review-loop.

**Делает ли он push или merge?**
Никогда. Если вы не выбрали «больше не спрашивать в этом репозитории», review-loop спрашивает перед каждым коммитом. Чтобы отменить этот выбор, попросите Claude отключить делегирование коммитов в review-loop.

**Будет ли он конфликтовать с другими моими плагинами?**
review-loop добавляет один skill, одного агента и один хук. Хук читает команды Bash и реагирует только на `git commit` и `git push`. Если вы не включили commit gate в этом репозитории, хук ничего не делает. Его имена начинаются с `review-loop:`, поэтому они не могут совпасть с именами из других плагинов. Если вы формулируете запрос обычными словами, Claude может выбрать другой skill для ревью. Команда всегда запускает review-loop.

**Что произойдёт, если сессия закончится посреди цикла?**
Запустите команду снова. Команда предложит два варианта: продолжить с того раунда и шага, где цикл остановился, или начать заново.

**Как его удалить?**

```
claude plugin uninstall review-loop@lim
claude plugin marketplace remove lim
```

Затем удалите `.git/lim/review-loop/` в каждом репозитории, где вы запускали review-loop.

## Как устроена разработка LIM

- **Сначала issue.** Каждое изменение начинается с issue и попадает в проект через pull request. Мейнтейнер вливает этот pull request через squash merge.
- **Отдельные версии для каждого плагина.** Каждый плагин следует Semantic Versioning, ведёт свой `CHANGELOG.md` и получает тег `<plugin>--v<version>`. Для minor и major релизов создаётся GitHub Release.
- **Небольшой размер намеренно.** У плагина один входной skill, `SKILL.md` короче 250 строк и только хуки, которые включаются по вашему выбору.
